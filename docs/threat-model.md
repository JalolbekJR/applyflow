# Threat Model

## Scope And Assumptions

Phase 3 implemented scope is the same-browser anonymous draft flow, candidate and experience
persistence, private PDF upload/metadata/replacement/deletion, local private storage, and
cleanup-supporting metadata/service boundaries that already exist. Public vacancies and
authenticated Django Admin remain trust-boundary neighbours.

The cleanup management command, cleanup scheduling, stale-orphan scanning, final submission, public
status lookup, document download, production object storage, deployment, monitoring platforms, and
malware scanning are out of scope. The first deployment remains intended to be same-origin over
HTTPS, but Phase 3 itself is local and must not process real candidate data.

The attacker can send arbitrary anonymous HTTP and multipart requests, modify UUIDs and payloads,
host a cross-site page, replay a stolen cookie, upload crafted bytes, and race requests. The
attacker does not begin with server filesystem, database, environment-secret, or authenticated
staff access. A stolen staff account is treated as a separate high-impact boundary failure.

## Components, Boundaries, Assets, And Entry Points

Trust boundaries:

1. Candidate browser to same-origin Nuxt/API routes: untrusted input, CSRF-bearing mutations, and an
   HttpOnly ownership cookie.
2. Django/DRF to the database: trusted application code enforcing object ownership, lifecycle,
   constraints, and short row locks.
3. Django document service to private storage: hostile file bytes cross into a non-public storage
   adapter; database and storage do not share one atomic transaction.
4. Authenticated staff browser to Django Admin: separate session authentication and authorization;
   Phase 3 exposes document metadata but no download.

Deferred cleanup boundary:

- Future cleanup command to database/private storage: privileged local operation with deletion
  authority and privacy-safe aggregate logs. This boundary is planned for Slice 8 and is not an
  active entry point today.

Assets:

- Draft ownership credentials and CSRF tokens.
- Candidate identity/contact data and experience text.
- Private CV contents, metadata, checksums, and storage keys.
- Draft and document integrity, vacancy ownership, and lifecycle state.
- Django Admin sessions and environment secrets.
- Pending-deletion metadata and deletion timestamps. Privacy-safe cleanup evidence is future
  command output.
- Backend availability, temporary-file capacity, and private-storage capacity.

Entry points:

- CSRF bootstrap, draft create/resolve/read/update/abandon, experience CRUD, document
  upload/metadata/replace/delete, public vacancy reads, and Django Admin.

Deferred entry points:

- Cleanup management command, stale-orphan scanning, and scheduled cleanup execution.

## Security Decisions And Residual Risk

- One active draft total is a privacy and simplicity decision, not a defence against device
  compromise. Cookie loss can leave an inaccessible active draft until expiry and permit a new
  draft because the system deliberately does not fingerprint the browser.
- Cookie credentials are bearer credentials. Phase 3 deliberately avoids fingerprints, accounts,
  email recovery, or device binding.
- CSRF remains mandatory even with SameSite cookies.
- File validation reduces format and storage risk but is not antivirus. Staff download is deferred,
  so no claim is made that files are safe to open.
- Database/storage consistency uses compensation and cleanup-supporting metadata because no
  cross-system transaction exists. Batch cleanup remains a Slice 8 implementation task.
- Local storage and SQLite are development capabilities. Production ACLs, backups, shared
  throttling, PostgreSQL concurrency, deployment headers, and monitoring remain unverified.

## Security Review Required For Final Phase 3 Acceptance

Before final Phase 3 handoff:

1. Preserve verified ownership, CSRF, response serialization, and no-secret/no-PII response
   controls for every candidate endpoint.
2. Reinspect logs and serializers for credentials, PII, filenames, checksums, and keys after
   cleanup work lands.
3. Repeat failure injection for cleanup, storage save/delete, and database persistence around
   upload and replacement.
4. Run or preserve cross-draft, cross-vacancy, cross-entry, cross-document, replay, expiry, and race
   tests.
5. Review the selected PDF parser version and reject any malware-scanning claim.
6. Verify no static, media, Admin, or API route exposes document content or storage location.
7. Repeat locking and conditional-uniqueness tests on PostgreSQL before production-readiness claims.
8. Treat deployment-only controls, including shared throttling, CSP reporting, proxy limits,
   monitoring, backups, and object-storage ACL evidence, as future production-readiness work.
